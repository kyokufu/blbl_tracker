# Development instructions

- Build a personal Bilibili-to-Notion statistics sync. Follow `IMPLEMENTATION_PLAN.md`; resolve its compatibility and live-API gates before enabling writes or scheduling.
- Use Python 3.12 and the standard library initially. Add a dependency only when it clearly reduces maintenance; pin and justify it. Use `unittest` and mock HTTP for deterministic offline tests.
- Preserve the existing Notion tracker. Query one explicitly configured data source, validate property IDs/types, and patch only configured statistics and the successful-sync timestamp. Never create/reorganize the database or change statuses, relations, content, or views automatically.
- Keep Notion and Bilibili HTTP clients separate. Always set timeouts, preserve TLS verification, bound retries/runtime, honor `Retry-After`, and stop Bilibili calls after an anti-bot block. No cookies, login scraping, proxy rotation, or challenge bypass.
- Validate the requested/returned BV ID, application status, and all four required counts. Reject booleans, negative counts, missing fields, and malformed responses; never substitute zeros. Never advance a timestamp after a failed fetch or update.
- Default to read-only dry-run; require an explicit write flag. Keep the same parsing/validation path in dry-run and apply mode. Isolate per-video failures and report partial failure with a nonzero exit status.
- Use environment variables for the Notion token and source identifier; use a local TOML mapping for schema compatibility. Never commit credentials, real database exports, private page content, or raw authenticated responses. Do not log headers, tokens, titles, or full URLs.
- Keep operation free: standard Linux GitHub runners only, no artifacts/caches/paid services by default, bounded execution, and a verified account spending hard stop before private-repository scheduling. Do not promise guaranteed unattended service.
- Test with `python -m unittest discover -s tests -v` once tests exist. Live tests must be explicit and use a user-approved test row; do not write to the production tracker as part of ordinary tests.
- Use the existing isolated checkout; do not create a worktree unless requested. Implementation is authorized. Live Notion writes require review of a successful dry run first; do not run apply or enable scheduled writes before that review.
- One-time URL discovery is separate (`python -m blbl_tracker.discovery`). Only explicitly approved, unambiguous, live-owner-verified matches for UID 19997041 may populate an empty existing `url`. Eligibility is Status=Published and Published Acc. contains B站. Never run discovery from recurring workflows; never trust an export's UID assertion as ownership proof. Private reports contain tracker data: keep them ignored and owner-readable only.
- Historical archive reconstruction uses `python -m blbl_tracker.archive preview` only. Cache metadata incrementally and distinguish failed lookups from confirmed owner mismatches. One BV is one record; Cover + Tab means a performance with scrolling TAB, not two uploads. Inspect all existing rows for BV identities; unknown work/artist/type/date remains a review item. Archive creations/approvals/apply are deferred until review of exact operations. Never change live schema or enable archive scheduling.
